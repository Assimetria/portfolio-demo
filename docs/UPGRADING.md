# Upgrading a customer repo to a new template version

> Purpose: the procedure for taking a new release of `Assimetria/product-template-informational` into a customer repo (`Assimetria/customer-<slug>`) without losing product work: what is merged, what is kept, how conflicts are resolved, and how the result is verified before it deploys.
> Last verified: 2026-09-20 (`scripts/@system/sync-upstream.sh`, `scripts/@system/check-system-sync.sh`, `.template-sync-protect.json`, `start.sh`, `.github/workflows/{ci,deploy}.yml`).
>
> The versioned upgrade tooling (release tags, per-version upgrade notes, automated PRs) is being built separately and will be documented in `docs/TEMPLATE-VERSIONING.md` (forthcoming). Until then this manual procedure is the supported path.

## 1. Ownership: what an upgrade may touch

| Path | Owner | On upgrade |
|---|---|---|
| `**/@system/**` (server, client, scripts, migrations) | template | replaced / merged from the template |
| `**/@custom/**` | product | never touched by the template |
| `brand.json`, `assets/`, `.config/` | product (written by Orkosi + the customer) | kept as-is |
| `VERSION`, `CHANGELOG.md`, `template-manifest.json` | template | taken from the template (they describe the template release, not the product) |
| `docs/*.md` (template docs) | template | taken from the template; product docs live in `docs/` with a product-specific name and are kept |
| `package.json` / lockfiles | shared | merged; `.template-sync-protect.json` lists deps that must not be re-added (`removed_deps`) or downgraded (`pinned_deps`) |
| `.github/workflows/*`, `Dockerfile`, `start.sh`, `buildspec-*.yml` | template | taken from the template (pipeline contract with Orkosi provisioning) |

Generated files (`client/src/app/styles/@custom/brand.css`, `client/src/config/@custom/info.js`, barrels under `@system`) are regenerated by `npm run prebuild`, so conflicts in them are never resolved by hand.

Product patches inside `@system` files survive only when wrapped in `// @sync-guard:<name>` ... `// @end-sync-guard` (also `#` comments). Anything else in `@system` is expected to be overwritten; move it to `@custom` before upgrading.

## 2. Procedure A — pull from the customer repo (git merge)

Work on `dev` (the default branch of a customer repo; `main` deploys).

```bash
git checkout dev && git pull
git remote add template https://github.com/Assimetria/product-template-informational.git 2>/dev/null || true
git fetch template --tags

# 1. see what changed in the template since the last upgrade
git log --oneline $(git merge-base HEAD template/main)..template/main -- '*@system*' Dockerfile start.sh .github | head -50

# 2. merge without committing so ownership can be enforced before the commit
git merge --no-ff --no-commit template/main

# 3. product-owned paths always win
git checkout HEAD -- brand.json assets .config 2>/dev/null || true
git checkout HEAD -- $(git diff --name-only --diff-filter=U | grep '@custom/' || true)

# 4. template-owned paths always take the template side
git checkout --theirs -- VERSION CHANGELOG.md template-manifest.json Dockerfile start.sh .github 2>/dev/null || true
git checkout --theirs -- $(git diff --name-only --diff-filter=U | grep '@system/' || true)
git add -A

# 5. anything still conflicted is shared (package.json, lockfiles, docs, config)
git diff --name-only --diff-filter=U
```

Resolve the remaining conflicts by hand, then continue with section 4.

If step 4 discarded a product change that lived in `@system`, recover it from `git show HEAD:<path>` and re-apply it either in `@custom` or inside an `@sync-guard` block, then open a template PR so the next upgrade does not repeat the exercise.

## 3. Procedure B — push from a template checkout (sync script)

Used by Orkosi and by maintainers who upgrade several products at once. From a checkout of the template at the target release:

```bash
git checkout v<version>            # or main
scripts/@system/sync-upstream.sh /path/to/customer-<slug>
```

The script finds the last `chore: sync with product-template <sha>` commit in the product, overwrites unmodified `@system` files, three-way merges (`git merge-file`) the ones the product changed, preserves `@sync-guard` regions and never writes into `@custom/`. It does not touch `brand.json`, assets or product docs. Commit in the product as `chore: sync with product-template <short-sha>`; that commit is the base for the next sync. `scripts/@system/check-system-sync.sh` lists any `@system` file that still differs from the template.

## 4. After the merge, before the commit

```bash
# dependencies (only if package.json / lockfiles changed)
npm ci && npm ci --prefix client && npm ci --prefix server

# regenerate brand outputs and route barrels — never hand-resolve these files
npm run prebuild

# gates that CI will run
cd client && npm run lint && npm test -- --ci && cd ..
cd server && NODE_ENV=test npm test -- --ci --forceExit && cd ..
npm run build
npm run docs:check

# migrations: list what the new template will apply on deploy (start.sh runs them once per boot)
cd server && npm run migrate:dry && cd ..
```

Migration rules: template migrations are additive and idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`); product migrations live in `server/src/db/migrations/@custom/` with their own sequence and always run after `@system`. A failing migration on a reachable database makes the container exit on purpose (`docs/DEPLOYMENT.md` section 3), so run `migrate:dry` against a copy of production data when the release notes mention schema changes, and take a backup first (`docs/RUNBOOK.md` section 13).

Commit:

```bash
git commit -m "chore: upgrade template to v<version>" -m "Template: Assimetria/product-template-informational@<sha>. Conflicts: <files>, resolved by <policy>."
```

## 5. Ship and verify

1. Push `dev`, open the PR `dev -> main`. CI must be green (lint, client tests, server tests, build, Docker smoke).
2. Merge. `deploy.yml` builds the image, pushes `:<sha>` and `:latest` and calls `start-deployment`.
3. Verify: `curl -s https://<app-url>/api/health | jq .version` ends with the new short SHA and `status` is `ok`; open `/`, submit the contact form once, check `/app/contact` shows it.
4. If anything is wrong, roll back per `docs/RUNBOOK.md` section 12 (previous ECR tag), then fix on `dev`.

## 6. Frequency and skipping releases

Upgrade at least once per template minor release; skipping releases is fine because both procedures merge against the current template state, not release by release. Read `CHANGELOG.md` for every skipped version — entries marked **breaking** name the `@custom` seams whose signature changed.
